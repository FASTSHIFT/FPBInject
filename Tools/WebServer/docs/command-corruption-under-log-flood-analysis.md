## 1. 结论

1. **现象**：一次测试里有 55 次文件下载以“整文件 CRC 不一致”失败，涉及 29 份不同的文件内容（按文件路径加设备端 CRC 区分）。其中 15 份失败了不止一次，同一份内容的设备端 CRC 每次都相同，上位机算出的 CRC 每次都不同。
2. **原因**：设备在持续输出大量日志时，上位机发来的命令行中间会丢掉一段连续字符，设备把残缺的命令当成合法命令执行了。最典型的是 `fseek` 的 `-a 20480 -r 0xE791` 变成 `-a 20xE791`：偏移被读成 20，校验码选项整个丢失。
3. **为什么 CRC 没拦住**：下位机的命令 CRC 是可选的，没带 `-r` 就不校验（`fl.c` 的 `fl_verify_crc`）；参数值解析出错只打印一行 `error:`，不中止命令（`argparse.c` 的 `argparse_error` 里 `exit` 被注释掉），命令照常用解析到一半的值执行。
4. **后果**：上位机 `1.6.12a3` 的 `fseek` 只要回复里有 `[FLOK]` 就算成功，不核对回复里的偏移（`FSEEK 20`）。之后读到的每个分块都是真实、分块 CRC 也正确的数据，只是位置错了，直到最后整文件 CRC 校验才暴露。
5. **新版是否解决**：`d562ba2` 已经有回复同步屏障，以及 `fseek`/`fwrite` 回复内容核对，能挡住一部分。但 `fread` 重试流程里 `fseek` 失败后仍然“继续读”，设备位置已经被改错，继续读还是会错位；整文件校验失败后也只能整个重来。第 9 节是针对这些缺口的修复。
6. **前一版推测的修正**：最初怀疑是“超时命令的回复晚到，被当成下一条命令的回复”。日志不支持这一点：没有任何一次 `fread`、`fseek`、`fcrc` 的回复比命令晚到超过 2 秒。主因是命令在设备一侧被截断。

## 2. 现象

### 2.1 调用方看到的

- 一次测试共 55 次下载失败，报错都是 `CRC mismatch: local 0x…, device 0x…`。
- 29 份不同的文件内容下载失败，其中 15 份失败了 2 次或更多。这 15 份在每次失败时：
  - 设备端 CRC 完全相同，说明设备上的文件没有变；
  - 上位机本地 CRC 全部不同，说明每次收到的内容都不一样。
- 分块 CRC（`fread` 回复里的 `crc=`）全部通过，否则 `fread` 会重试。问题只在最后的整文件校验里出现。
- 失败集中在设备持续高频输出日志的场景。这些场景下 `fread`/`fseek` 命令的回显不规范比例是 2.86%，其他场景只有 0.14%，相差约 20 倍。

### 2.2 串口原始日志里看到的

设备到主机方向的原始日志同时记录了命令回显、回复和设备的业务日志。下面两个例子把夹在中间的业务日志行省略了。

**例 A：`fseek` 被截断后仍然执行**

```
[FLOK] FREAD 512 bytes crc=0x320F data=<base64>
[FLEND]
fl>fl -c fseek -a 20xE791                  <- 上位机发的是 -a 20480 -r 0xE791
error: option `-a` expects an address value
[FLOK] FSEEK 20                            <- 设备 seek 到了 20
[FLEND]
fl>fl -c fread -l 512
[FLOK] FREAD 512 bytes crc=<crc> data=...  <- 从偏移 20 读，上位机以为是 20480
```

命令中间 `480 -r 0` 这 8 个字符不见了。`-r` 选项也一起丢了，所以设备没有校验。

**例 B：`fread` 的结尾丢失，与下一条命令粘成一行**

```
fl -c fread -l 5fl -c fseek -a 155648 -r 0x79C9
error: option `-l` expects an integer value
[FLOK] FSEEK 155648
[FLEND]
```

`fl -c fread -l 512` 的结尾 `12` 和换行丢了，后面紧跟着的 `fseek` 命令被接在同一行。设备解析时：`-l 5fl` 报错但值已存成 5；后面再来的 `-c fseek` 覆盖了前面的 `-c fread`；`-a 155648 -r 0x79C9` 完整且校验正确。结果设备只回了一个 `FSEEK` 回复，上位机的 `fread` 收到的是 `[FLOK] FSEEK 155648`。

丢失的是连续的一段字符，更像接收缓冲溢出。本次抓取只有设备到主机方向，无法确认丢字符发生在串口驱动、设备接收缓冲，还是设备端 shell 的行编辑被日志输出打断。

## 3. 为什么残缺命令能执行成功

### 3.1 CRC 是可选的

`App/func_loader/fl.c`：

- `fl_exec_cmd` 在解析参数前把 `args.crc` 初始化为 `-1`（第 181 行）。
- `fl_verify_crc(int crc, uint16_t calc)`（第 113 行）：`crc < 0` 时直接返回 true。注释写的是“CRC 匹配或未提供时返回 true”。
- `fl_cmd_fseek`（`fl_cmd_file.c` 第 207 行）只在 `args->crc` 有值时才校验，校验范围是 4 字节的偏移值。

所以 CRC 保护的是“偏移值有没有被改坏”，保护不了“校验码选项本身被丢掉”。例 A 里 `-r` 丢了，校验被整个跳过。

### 3.2 参数值解析出错不中止命令

`App/func_loader/argparse/argparse.c`：

- `argparse_error`（第 31 行）只往 stderr 打印 `error: option ... expects ...`，`exit(EXIT_FAILURE)` 被注释掉（第 38 行）。
- 整数和地址选项（第 88、104 行）先用 `strtol`/`strtoul` 把值存下来，发现后面有多余字符才调用 `argparse_error`。值已经写进参数结构。
- `fl_argparse_parse` 的返回值是剩余的位置参数个数，未知选项返回 `EXIT_FAILURE`。`fl.c` 第 210 行只在返回值大于 0 时回复 `[FLERR] Invalid arguments`。选项值非法既不增加剩余参数，也不是未知选项，所以命令继续执行。

例 A：`strtoul("20xE791")` 得到 20，打印错误，没有剩余参数，`-r` 缺失，于是 `fseek(20)` 被执行。

### 3.3 重复选项后者覆盖前者

例 B 里两条命令粘在一起，`-c fread` 之后又出现 `-c fseek`，后者覆盖前者。第二条命令本身是完整的，包括校验码，所以设备执行并回复了 `FSEEK`。

### 3.4 其他命令的 CRC 覆盖情况

按 `fl_cmd_*.c` 里 `fl_verify_crc` 的调用统计：

- 带可选 CRC：`fopen`、`fwrite`、`fseek`、`fstat`、`flist`、`fremove`、`fmkdir`、`frename`、`exec`、`alloc`、`upload`、`read`、`write`、`patch` 系列。
- 没有 CRC：`fread` 的长度参数 `-l`、`fclose`、`fcrc` 的 `-a`/`-l`，以及 `ping`、`echo`、`info`。

`fread` 的 `-l` 没有校验，`-l 512` 被截成 `-l 5` 会只读 5 个字节，回复里的分块 CRC 仍然正确。上位机用实际读到的长度推进偏移，所以这种情况下位置不会错，但会让传输变慢。

## 4. 统计

口径：设备端串口日志中，从 `fopen` 到 `fclose` 算一个下载会话，共 1400 个。“失败”指会话里最后一个 `fcrc` 回复的 CRC，与调用方日志里记录的失败下载的设备端 CRC 相同。这个口径会把同一文件的多次重试各算一次，所以失败会话数（71）比调用方记录的失败次数（55）多。

**命令层面**

| 项目 | 数量 |
|------|------|
| `fread` 命令 | 388,529 |
| 其中没有任何回复 | 1,235 |
| 其中收到的不是 `FREAD` 回复 | 165 |
| `fseek` 命令 | 2,368 |
| 其中回显不规范（命令残缺） | 346（14.6%） |
| 残缺的 `fseek`：设备返回 `[FLERR]` 拒绝 | 177 |
| 残缺的 `fseek`：设备返回 `[FLOK]` 并执行 | 168 |
| 残缺的 `fseek`：没有回复 | 1 |

`fseek` 的残缺比例高于 `fread`，因为它的参数更长，可能被丢的字符更多。

**会话层面**

| 条件 | 会话数 | 其中失败 |
|------|-------:|---------:|
| 含残缺 `fseek` | 106 | 59 |
| 不含残缺 `fseek` | 1294 | 12 |
| 含残缺 `fseek` 或命令粘连 | 253 | 64 |
| 其余 | 1147 | 7 |
| 含任一类异常（残缺、粘连、`fread` 无回复、`fread` 收到非 `FREAD` 回复） | 429 | 68 |
| 无任何异常 | 971 | 3 |

无异常的会话里仍有 3 个失败，目前没有找到原因。含残缺 `fseek` 的会话里，有 47 个没有失败（`fseek` 被拒绝后重试成功，或残缺没有造成错位）。

## 5. 上位机现状核对（`main`，`d562ba2`）

### 5.1 已经有的防护

- `serial_protocol.py` 的 `_transact`（第 339 行）每次发送前调用 `reset_input_buffer()`，并在无回复时按次数重发。
- `serial_resync.py`：发一条带随机内容的 `echo` 作为屏障，读到它自己的回复为止，之前的内容当作过期回复丢弃（提交 `d7ea09c`）。
- `file_transfer.py` 的 `_reply_problem`（第 161 行）：回复必须恰好有一个结果标记；没有回复、混合回复、与 `expect` 不符的回复都判失败，并让下一条命令先做屏障。
- `fseek` 带 `expect=FSEEK\s+{offset}\b`（第 562 行），`fwrite` 带 `expect=FWRITE\s+{n}\s+bytes`（第 276 行）。例 A 里的 `FSEEK 20` 与期望的 `FSEEK 20480` 不符，在新版里会被判为失败。

### 5.2 仍然存在的缺口（`d562ba2` 时；修复见第 9 节）

1. **`fseek` 失败后继续读。** `fread` 的重试流程（第 299 行起）在 `fseek` 失败时只记录日志，注释写着 “Continue anyway, maybe the read will work”（第 334 行）。例 A 里设备已经 seek 到了错误位置，继续读还是读到错位的数据，最终仍是整文件 CRC 不一致。`fwrite` 的重试流程同样有这句（第 271 行）。
2. **`fread` 没有 `expect`，回复里也没有偏移。** `FREAD` 回复只有长度、分块 CRC 和数据，没有数据所在的位置，上位机无法核对一个分块是不是自己要的那一块。
3. **整文件失败的代价高。** `download()` 在整文件 CRC 不一致时返回失败，调用方只能整个文件重新下载，每次重试都面临同样的风险。一个 600 KB 的文件约 1180 个分块，只要一个分块位置错就整个失败。

## 6. 建议

### 6.1 上位机（优先）

1. `fread`/`fwrite` 重试流程里，`fseek` 失败时重发 `fseek` 并核对偏移；多次仍失败就放弃当前分块并做一次屏障同步，不要继续读写。
2. `download()` 在整文件校验失败后，用 `fcrc` 的分段模式（`-a`/`-l`）逐段与本地分块对比，只重读不一致的区间，不整文件重来。
3. 失败时在错误信息里带上最近一次 `fseek` 的预期偏移和实际回复，便于定位。

### 6.2 下位机

1. **参数值非法要中止命令。** 让 `argparse_error` 记录错误，`fl_argparse_parse` 返回失败，`fl_exec_cmd` 回复 `[FLERR] Invalid arguments`。`argparse/` 是第三方代码的拷贝，建议通过新增的严格模式标志启用，不改变其他使用者的行为。
2. **会改变设备状态的命令不再接受缺失的 CRC。** `fseek`、`fopen`、`fwrite`、`fremove`、`fmkdir`、`frename` 等，上位机总是带 `-r`。
3. **让位置可核对。** 例如 `fread` 回复增加偏移字段。需要先确认老版本上位机对多出的字段是否兼容：`file_transfer.py` 的解析正则要求 `bytes` 后面直接跟 `crc=`。
4. `fread -l`、`fcrc -a/-l` 增加可选的参数校验码，覆盖当前没有保护的参数。

### 6.3 降低丢字符概率

1. 评估 TX 分片（`serial_tx_fragment_size`、`serial_tx_fragment_delay`，默认关闭，见 `tx-fragment-auto-adapt-design.md`）对这类场景是否有效。该设计原本针对 PC 一侧串口驱动丢包，这里丢字符的位置不确定，效果需要实验。
2. 在测试期间降低设备的日志输出量，是最直接的办法。

### 6.4 诊断

串口日志目前把两个方向混在一起，只有设备回显。建议在上位机侧单独记录每条发出命令的完整文本和时间戳，便于直接比对“发出的”和“设备收到的”。

## 8. 局限

- 数据来自一台设备、一次约 3.2 小时的抓取，抓取时上位机是 `1.6.12a3`。`main` 上的行为来自代码阅读，没有在设备上验证。
- 设备串口日志只有设备到主机方向，丢字符发生的位置是从回显推断的。
- 原始日志的时间戳按批次记录，精度不足以判断小于 1 秒的延迟，“回复没有晚到超过 2 秒”只能说明没有明显的长延迟。
- 会话是否失败按设备端 CRC 与调用方记录匹配判定，是近似口径。

## 9. 修复

### 9.1 上位机（`Tools/WebServer`）

| 建议 | 做法 | 位置 |
|------|------|------|
| 6.1 第 1 条 | `fread`/`fwrite` 重试前的 `fseek` 改为 `_seek_for_retry`：回复必须是 `FSEEK <偏移>` 且偏移相符，否则重发 `fseek`，最多 3 次。仍未确认就放弃这一次尝试，不再读写，转入下一次重试（用完重试次数则报 `Cannot reposition to offset N`）。原来的“继续读”不再存在。 | `core/file_transfer.py` |
| 6.1 第 2 条 | 新增 `repair_download`：整文件 CRC 不一致后，用 `fcrc -a/-l` 按 32 KB 段与本地数据比较，不一致的段再按 2 KB 片比较，只把不一致的片重新 `fseek`+`fread`，最多 3 轮。`download()`（CLI、SDK、同步接口）和流式下载接口 `/api/transfer/download` 都会在报错前先修复。 | `core/file_transfer.py`、`app/routes/transfer.py` |
| 6.1 第 3 条 | 确认不了位置时，日志和错误信息带上期望偏移和设备最后一次回复；下载失败的信息带上修复失败的原因。 | 同上 |
| 附带 | 整文件校验时，连续两次看到同一个错误的大小和 CRC，就不再重复校验（设备上的内容没有变，再问没有用），直接进入修复。以前要做 `transfer_max_retries + 1` 次。 | `_verify_crc_with_retry` |

没有改动的上位机建议：6.4 的发送端日志。

### 9.2 下位机（`App/func_loader`）

- 6.2 第 1 条：`argparse` 增加 `ARGPARSE_STRICT_VALUES` 标志。带标志时，任何选项值的错误（`-a 20xE791`、缺少值、超出范围）都会让整个解析失败，`fl_exec_cmd` 回复 `[FLERR] Invalid arguments`，命令不执行。`fl_exec_cmd` 使用该标志，别的使用者不受影响。两条粘在一起的命令（例 B 中的 `-l 5fl -c fseek …`）也因为 `-l 5fl` 不是合法整数而被拒绝。
- 没有做：
  - 6.2 第 2 条（会改变状态的命令必须带 CRC）：手工在终端里敲命令会立刻失败，需要先确定要不要保留这种用法。
  - 6.2 第 3、4 条（`fread` 回复带偏移、`fread -l` 和 `fcrc` 加参数校验）：要改回复格式，需要先评估老版本上位机的兼容性。第 9.1 的位置确认和修复已经覆盖了错位的后果。

### 9.3 测试

- 下位机：`fseek -a 20xE791` 被拒绝，`FSEEK` 不出现；粘连的两条命令被拒绝；合法命令照常执行；缺值的选项返回 `FL_ERR_PARSE`。去掉标志后这些测试失败。
- 上位机：用文件模型在任意一次 `fread` 返回错位数据的位置注入错误，下载仍然得到正确的文件；多个错位分块、只重读不一致的片、`find_bad_ranges` 定位到具体的 2 KB 片、修复不了时报 `repair failed`；`fseek` 一直落不到位置时 `fread`/`fwrite` 不再继续读写；`fseek` 重发几次后落到位置才继续。
- 流式下载接口：修复成功得到正确的数据，修复失败报 `repair failed`。

### 9.4 设备上的复测

复测用的设备带有第 9.2 节的下位机修改（严格解析）。上位机分两种：旧版是已发布的 `1.6.13a1`（有回复同步屏障，没有 seek 确认和修复），新版是带第 9.1 节修改的版本。

**一、混合压测（上传、下载、`exec`，设备 `/tmp`）**

文件大小在 1 KB 到 700 KB 之间随机，上传后用 `exec` 核对，再下载并与本地逐字节比较，最后删除。

| 场景 | 结果 |
|------|------|
| 没有额外日志，10 分钟 | 51 次上传、51 次下载、155 次 `exec` 全部成功，下载的内容与本地一致。每个方向合计约 10 MB。 |

**二、故障注入（真机、新固件）**

上位机一侧模拟第 2 节的两种损坏，其余都是真的设备在执行：

- 每 40 次 `fread`，设备正常执行，但回复在到达上位机前被丢掉（设备的文件位置已经往前走了，上位机要靠重试里的 `fseek` 回到原位）。
- 一半的 `fseek` 请求行被写成 `-a 20xE791` 这样的残缺形式（`-a 20480 -r 0xE791` 丢掉中间一段）。

每轮下载一个 200 KB 的随机文件，共 4 轮，新旧版本使用同样的随机种子和注入方式：

| 上位机 | 正确的下载 | 现象 |
|--------|-----------:|------|
| 旧版 `1.6.13a1` | 0 / 4 | 每次都是 `CRC mismatch`。本地 CRC 每次不同，设备端 CRC 三次相同，与第 1 节描述的现象一致。 |
| 新版 | 4 / 4 | 4 轮里丢了 28 个回复、写坏了 36 条 `fseek`，下载的内容仍然完全一致。 |

新固件会拒绝残缺的 `fseek`（位置不变），旧版上位机在拒绝之后仍然“继续读”，而这时设备位置已经因为丢回复的那次 `fread` 往前走了，所以读到错位的数据。新版上位机重发 `fseek` 直到偏移得到确认，才继续读。这一组结果是对第 9.1 节第一条的直接验证。

**局限**：没有在真实的高日志场景里复现原始问题，注入的损坏是模拟的；旧版上位机配新固件的组合，不能代表原来那台设备上的全部情况。第 7 节的第 1、3 项（高频日志下的失败率、TX 分片）仍然没有数据。
